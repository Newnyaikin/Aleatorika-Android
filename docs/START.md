# Публикация Алеаторики: пошагово

## 1. Подготовьте компьютер

1. Создайте аккаунт на https://github.com, подтвердите email.
2. Установите Git: https://git-scm.com/downloads.
3. Установите VS Code: https://code.visualstudio.com/.
4. После установки Git перезапустите VS Code.
5. Распакуйте нужный ZIP в обычную папку. Не работайте внутри ZIP.
6. В VS Code откройте **File → Open Folder** и выберите именно корень одного проекта. Не открывайте общую папку, содержащую сразу Android и Web.

Откройте **Terminal → New Terminal**. Проверьте:

```bash
git --version
```

Первый раз задайте имя автора и email. Замените значения своими, не копируйте примеры как реальные данные:

```bash
git config --global user.name "Ваше имя"
git config --global user.email "Ваш email для коммитов"
```

Email становится частью истории коммитов. Если не хотите показывать личную почту, возьмите свой точный адрес `noreply` из GitHub → Settings → Emails. Его нельзя угадывать.

## 2. Опубликуйте папку из VS Code

Отдельно выполните эти действия для Android, затем для Web:

1. Откройте **Source Control** (`Ctrl+Shift+G`).
2. Нажмите **Initialize Repository**. Если репозиторий уже инициализирован, этот шаг пропустите.
3. Просмотрите список файлов. Папка `.github/` обязательно должна присутствовать. В Android также нужны `android/` и `shared/`. Приватных ключей, паролей, `local.properties` и папок сборки в списке быть не должно.
4. Нажмите **Stage All Changes** — значок `+` рядом с Changes.
5. Введите сообщение `Initial project` и нажмите **Commit**.
6. В терминале выполните команду для имени основной ветки:

```bash
git branch -M main
```

7. Нажмите **Publish Branch / Publish to GitHub**. Также команда доступна через `Ctrl+Shift+P → Publish to GitHub`.
8. Разрешите вход в GitHub в открывшемся браузере и вернитесь в VS Code. Пароль или токен не нужно записывать в файлы проекта.
9. Выберите имя нового репозитория, указанное ниже, и **Public repository**. Для общедоступных исходников/сайта это самый простой вариант; GitHub Pages в приватных репозиториях зависит от плана.
10. Откройте созданный репозиторий на GitHub. В корне должны быть файлы проекта, а не один ZIP и не лишняя внешняя папка.

Если вы заранее создали пустой репозиторий на сайте, вместо Publish подключите его как remote, заменив адрес своим:

```bash
git remote add origin https://github.com/YOUR_LOGIN/YOUR_REPOSITORY.git
git push -u origin main
```

Не выполняйте `remote add`, если `origin` уже есть. Проверить можно командой `git remote -v`. Не используйте принудительную перезапись `push --force`.

## 3. Как отправлять дальнейшие изменения

Измените файлы, сохраните их. В Source Control выполните **Stage All Changes → Commit → Sync Changes**. В сообщении коммита кратко опишите изменение. Если появилась кнопка Pull, сначала получите изменения с GitHub и разрешите конфликты, а не перезаписывайте историю.

Android и Web теперь независимы. Изменение в одной папке НЕ переносится автоматически в другую. Если исправляете общую музыкальную логику или правила, обновляйте соответствующие реализации в обоих репозиториях.

## Android: первая автоматическая сборка

Рекомендуемое имя репозитория: **aleatorika-android**.

Структура в корне:

```text
.github/workflows/android.yml
android/
shared/
tools/
docs/
README.md
.gitignore
```

1. После первой отправки в `main` откройте **Actions**.
2. Выберите **Android - build APK and release**.
3. Откройте самый свежий запуск. Дождитесь зелёного статуса. SDK, JDK и Gradle установятся на GitHub автоматически; локальная Android Studio для этого не нужна.
4. На странице запуска прокрутите до **Artifacts**.
5. Скачайте **Aleatorika-Android-N**, где N — номер запуска. Для скачивания Artifacts нужно войти в GitHub.
6. Распакуйте скачанный ZIP.

Внутри:

| Файл | Для чего |
| --- | --- |
| `Aleatorika-1.0-test.apk` | Установочная тестовая сборка. Можно проверить приложение на телефоне. |
| `Aleatorika-1.0-unsigned.apk` | Неподписанный release APK. До подписи его нельзя установить. |
| `Aleatorika-1.0.apk` | Появится только после настройки четырёх secrets подписи. Это APK с вашим постоянным ключом. |
| `Aleatorika-Android-source.zip` | Исходники того же коммита. |

Повторить сборку без изменения кода: **Actions → Android - build APK and release → Run workflow → main → Run workflow**. Если Run workflow ещё не виден, убедитесь, что файл workflow уже находится в основной ветке.

Срок хранения Artifacts — 30 дней. Для публичной ссылки на APK удобнее Releases: такой релиз не зависит от срока хранения Artifacts.

### Почему тестовая сборка может не обновиться поверх старой

Временный GitHub runner может создать новый debug-ключ на каждом запуске. Система Android не установит такой APK поверх приложения с другой подписью, даже если оба имеют версию 1.0. Удаление приложения уничтожает локальные данные. Не удаляйте его, если нужна статистика. Для постоянного распространения используйте собственный неизменный ключ: [SIGNING.md](SIGNING.md).

### Автоматический Android Release

Делайте это из терминала VS Code, открытого именно в Android-проекте, после отправки коммита в GitHub:

```bash
git tag v1.0.0
git push origin v1.0.0
```

После успешной сборки Actions сам создаст GitHub Release и прикрепит APK и архив исходников. Без secrets подписи создаётся **Pre-release** с тестовым APK. С правильно настроенными secrets создаётся обычный релиз с постоянной подписью. Неподписанный APK остаётся только в Artifacts, а не предлагается пользователям релиза.

Релиз находится справа в **Releases**. Оттуда люди могут скачивать приложенные APK. Публикация APK на GitHub не равна публикации в Google Play.

Если `v1.0.0` уже есть, используйте новый тег, например `v1.0.0-r2`. Не удаляйте и не переносите опубликованные теги. Имя тега не меняет `versionName` или `versionCode` автоматически. Сейчас сохранены 1.0 и code 2. Для Google Play при обновлениях потребуется увеличивать versionCode.

### Если сборка красная

Откройте запуск → **build** → первый красный шаг. Скопируйте текст ошибки, но не секреты. Если ошибка в Gradle — смотрите шаг Build APK; если `403` при создании релиза — проверьте ограничения GitHub Actions/токена в настройках репозитория или организации. Workflow уже запрашивает `contents: write` только для job публикации релиза. Отдельный Personal Access Token для обычного собственного репозитория не нужен.

Если configured signing secrets указаны лишь частично, сборка специально завершится ошибкой, а не незаметно выпустит неподписанный production APK.
